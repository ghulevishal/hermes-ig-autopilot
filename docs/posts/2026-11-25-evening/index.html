The retry that charged the customer twice

A timeout tells you nothing about whether your side effect ran — and in an agent that retries on its own, that ambiguity turns one charge into two. The fix is one idempotency key per action, not per attempt.

analysis2026-11-25·5 min read·on Instagram

The failure nobody designs for

You wire an agent to a real API. A tool call charges a card, sends an email, opens a ticket, books a slot. It works in testing, because in testing the network is perfect.

In production the network is not perfect, and the first time a request times out you discover the thing the happy path hid: a timeout is silence, not a "no." The call can fail in three different places, and from the caller's side all three are indistinguishable — a timeout and no answer:

  • Before the request reaches the server. Nothing happened. A retry is safe.
  • Halfway through. The server started the work and something broke. Maybe the charge ran, maybe it didn't.
  • After the work finished. The money moved, then the connection dropped before the response got back.

Stripe's engineering team starts their idempotency write-up from exactly this blunt fact. The client cannot tell these apart, so to converge its own state with the server's it does the only thing it can: it retries. And without a guard, "retry" means "do the whole thing again." The charge that already succeeded in case three runs a second time.

Idempotency: the same operation, once

An operation is idempotent if doing it twice has the same effect as doing it once. GET only reads. DELETE the same row twice and it is just as deleted. The problem is the mutating verbs — POST, PATCH — where a second execution is a second real-world event.

The fix is to make those endpoints idempotent with an idempotency key: a unique string the client generates, attached to the request in an Idempotency-Key header. The server correlates the key with the state of that request on its end. The crucial property, in Stripe's own words, is that the operation "can be called any number of times while guaranteeing that side effects only occur once."

The mechanics on the server are deliberately simple:

1. First time a key arrives: no record exists, so run the work and store the response (status code and body) against the key. 2. Any later request with the same key: a record exists, so return the stored response and run nothing.

That is the whole idea. A key does not mean "try again from scratch." It means "tell me what happened to this request."

The one rule everything hinges on

Read the client side carefully, because this is where agents break it:

The key is made once, before the first attempt, and every retry of that operation reuses it.

Stripe suggests a V4 UUID or any string with enough entropy to avoid collisions, up to 255 characters, and warns against putting sensitive data (emails, personal identifiers) in the key. The randomness is not the point — the stability across retries is. A perfectly random key regenerated on every attempt is worse than useless: it guarantees a new operation each time.

Why agents walk straight into it

In a plain client you write the retry loop yourself and it is obvious where the key comes from. An agent stack hides the retries across layers, and each layer looks like a fresh request:

  • The model SDK retries on a transport error.
  • Your orchestration loop retries a failed tool call.
  • The agent itself, after a crash or a restart, re-decides to call the tool — a retry that does not know it is a retry.

If the key is minted inside any of those — Idempotency-Key: str(uuid4()) computed at call time — every retry carries a brand-new key, and the server, correctly, treats each as a distinct operation. You get the double charge the mechanism was supposed to prevent, and your logs show two clean 200s.

The fix is to source the key from the logical action, not the attempt. Derive it deterministically from something stable — order_id + the operation name — or generate it once and persist it before the first call, so every retry and every process restart reads the same value. The model is non-deterministic; the key must not be. It has to come from the task, stored outside the model's context, where a restart can find it again.

What it looks like in the terminal

# timed out. did the charge run? unknown
$ POST /charges   Idempotency-Key: 9f2c...a1
curl (28): operation timed out
# retry mints a new uuid4() -> new key
$ POST /charges   Idempotency-Key: 4b8e...c7
200  amount=1000   <- a SECOND charge
$ POST /charges   Idempotency-Key: 9f2c...a1
200  Idempotent-Replay: true  (no new charge)

Same key in, stored response back — the charge runs once. A fresh key per attempt is a fresh charge. (Ids and timings illustrative; the headers and replay behaviour are Stripe's.)

The server side, and its edges

If you implement the receiving end yourself — because the side effect is your own service, not a vendor's — Brandur Leach's Postgres design and the IETF Idempotency-Key draft give you the shape:

SituationResponse
Key unseenInsert a partial record (keyed on account + key), do the work, store the result
Key seen, completedReturn the stored response, run nothing
Key seen, still in flight409 Conflict — tell the client to retry for a definite answer later
Same key, different paramsError — this is misuse, not a replay
Transient failure (429 / 503)Do not store a result; remove the partial so the client can retry

A unique index on (account_id, idempotency_key) makes the duplicate check atomic. The same key may map to different requests across different accounts, so scope the uniqueness by account.

Where it stops

  • Keys expire. Stripe retains API v1 keys for at least 24 hours, then may prune them; reuse after pruning executes a new request. (Stripe's newer API v2 widens this to a 30-day window and retries failed work to completion rather than replaying a stored response — check which you're on.) Keep your own retries inside the window and reconcile, don't retry blindly, past it.
  • It makes retries safe; it does not make them polite. You still need capped attempts, backoff and jitter, or you trade a double charge for a retry storm.
  • It protects one operation, not a workflow. "Charge, then ship" needs the key on the charge and a way to resume the ship step; an idempotency key on the outer call won't make a multi-step side effect atomic.

The one line to keep

A retry is only safe if it carries a key it didn't just invent. Generate it once, tie it to the action, and reuse it on every attempt — then a timeout stops being a question you can't answer and becomes one the server answers for you.
