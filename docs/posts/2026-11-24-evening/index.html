Structured output is not validated output

Constrained decoding guarantees the shape of your JSON and nothing about whether the values are true — so build the semantic layer the schema can't.

analysis2026-11-24·5 min read·on Instagram

The green parse that lies

Structured outputs are now the default way an LLM hands you data. OpenAI's response_format: json_schema with strict: true, Anthropic's output_config.format, Gemini's responseSchema, Bedrock's constrained decoding — all of them compile your JSON Schema into a grammar and mask tokens at generation time so the model physically cannot emit output that breaks the schema. That is a real, valuable guarantee. You can delete the try/except JSON-repair loop.

But it covers exactly one thing: structural conformance. The grammar knows price must be a number. It has no idea the price of this product is 49.99. It knows currency must be a three-letter enum. It cannot know the order was placed in euros. The constraint operates on token syntax; correctness lives in semantics the grammar was never given.

OpenAI says this in the same announcement that reports the headline number. Their gpt-4o-2024-08-06 model scored a "perfect 100%" on their schema-conformance eval. Two paragraphs later: "Structured Outputs doesn't prevent all kinds of model mistakes. For example, the model may still make mistakes within the values of the JSON object." A 2026 arXiv study ("Constrained Decoding Eliminates Structural Failures in Small LLMs but Reveals a Scale-Dependent Semantic Gap") states the same conclusion formally: schema conformance is necessary but not sufficient for semantic correctness.

The schema-on-read trap

Here is the failure pattern, and it is everywhere. A team adopts structured outputs, wires the response straight into a Pydantic model or a TypeScript interface, and the moment deserialization succeeds, the data is treated as trusted. The validator and the parser have silently merged into one step: parsing succeeded, therefore the data is good.

Parsing only proves the bytes matched the type. Call the result the well-formed nonsense class of bug. Every value is the right type. Every required key is present. Every enum is legal. And the record is still wrong:

FieldValueWhy it's wrong
ship_date"2026-02-30"Valid ISO-8601 string; that date does not exist
discount_pct140A number; the only meaningful range is 0–100
sku"PRD-44182"Perfectly formatted; matches no row in your catalog
assignee"billing-svc"A legal enum member; that service was decommissioned last quarter
total84.00A number; it does not equal sum(line_items) — the model computed it alone

None of these trips a schema check. All of them are bugs. The schema validated that you received an object of the right kind; it could not validate that the object describes something real. The trap is that the green parse looks like a validation pass, so the team that would never trust an unvalidated user form will happily trust an unvalidated model output — because the model output arrived with a schema attached.

This is familiar ground for anyone who has worked a trust boundary. You never trusted the amount field on an inbound payment message because it parsed as a number. You validated it against limits, against the account, against the ledger. A model response is inbound data from an untrusted source. The schema is the wire format. It is not the validation.

Two more things the schema quietly doesn't do

Validation keywords are not all enforced. OpenAI's strict mode supports a subset of JSON Schema. Keywords like pattern, format, minLength and minimum are accepted but not guaranteed by constrained decoding — if you need a regex honored or a number kept in range, you still check it yourself after the response lands. Anthropic's SDK helpers go further and strip minimum/maximum/minLength before sending, re-validating against your original schema only if the helper does response validation. Assuming minimum: 0 was enforced at generation is how a negative quantity reaches your code.

Reasoning models can be made worse by the constraint. An independent 2026 battery across 12 APIs found that forcing a reasoning model's output through the constrained channel can interrupt its thinking and commit it to a confidently wrong number — every response schema-valid, up to 7 of 8 wrong on some model/task pairs. Turning extended thinking off recovered most of them. The lesson is not "never constrain"; it is that the constrained channel and the model's reasoning interact, so measure value correctness on your model, not just schema validity.

Build the layer the schema can't

Match the remedy to the failure. A wrong value is a semantic failure, so the fix is semantic validation, not a tighter schema.

  • Validate structure and value in two distinct steps. Step one: the schema (free, from the decoder). Step two: assert the business rules the grammar never saw.
  • Check values against a source only you control. Range and calendar checks catch 140 and 2026-02-30. A foreign-key lookup catches the phantom sku. A recomputation catches a total that disagrees with its line items. A checksum catches a mangled identifier. The schema is syntax; truth is a database, the source document, or arithmetic you run yourself.
  • On failure, reject and reprompt with the validator's own error, so the model sees exactly what was wrong (discount_pct=140, must be 0–100). Cap retries — 2 is usually enough — then fall back to a deterministic path or surface the item for review. An uncapped reprompt loop is a cost and latency incident waiting for a bad input.
  • Always branch on stop_reason / refusal. A refusal or a max_tokens cutoff ends the turn before the JSON is complete; a truncated object often parses as a valid partial object, so the schema check passes on half a record. Check the finish reason before you trust the parse.
  • Log raw and parsed output, and emit a validation-failure metric. Because the nonsense is well-formed, nothing else in your stack will alarm. Silent semantic regressions after a model swap only show up if you are measuring value correctness, not parse success.

Where this doesn't apply

If the output never feeds application logic — a draft for a human to read, a brainstorm, free text — schema validity is plenty and a semantic layer is overhead. The discipline is for the path where a value flows into a decision, a write, or a downstream call without a human checkpoint. There, treat every model output the way you treat every other input crossing a trust boundary: parsing proves the bytes matched the type; it never proves the value is real.
