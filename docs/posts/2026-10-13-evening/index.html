My agent ran for 8 hours and published nothing

A scheduled job fired at 09:00 and posted at 22:50. The thirteen hours in between were a single model call with no deadline, no checkpoint, and no alarm — three omissions that turn an unattended agent into a silent failure.

analysis2026-10-13·3 min read·on Instagram

The job is supposed to be boring. At 09:00 a cron job researches a topic, writes a spec, renders six slides, writes an article, and publishes. End to end it is about three minutes of real work: the renderer produces six 1080×1350 JPEGs in well under a second, and the publish chain is ten HTTP calls.

It fired at 09:00. It published at 22:50.

What the run log actually said

`` RuntimeError: Operation interrupted: waiting for model response (922.4s elapsed). ``

That is the morning job. The evening job died the same way at 1537.8 seconds. Two runs, 15 and 25 minutes, both spent waiting on a single model response that never arrived, both killed by the runtime with everything they had produced still in memory.

The part that matters is not the hang. Upstream APIs hang; that is ordinary. The problem is what the hang cost: the run had already researched the topic, written the spec, and rendered all six slides to disk. All of it was discarded, and the next run started from zero and did it again.

Three omissions, in order of severity

No deadline on the model call. The call had no timeout, so the only thing that eventually stopped it was the runtime's own interrupt at a quarter of an hour. A model call is a network call to someone else's machine. It gets a deadline for the same reason every other network call does.

No checkpoint between stages. The pipeline has four distinct stages — research, spec, render, publish — and they have wildly different reliability. Research and writing are slow, non-deterministic model calls. Rendering and publishing are fast, deterministic scripts. Putting them in one process means the reliable 2% inherits the failure rate of the flaky 98%.

No alarm on the missed window. A 09:00 job that publishes at 22:50 has failed, even though it eventually succeeded. Nobody was told. The catch-up fire quietly covered for it, which is worse than a clean failure: it produced a post at an hour nobody chose, and it looked like the system working.

The five guards

Reusable on any agent you leave running unattended.

GuardWhy
Deadline every model call — 120s, not infinityWithout one, slow is indistinguishable from stuck
Checkpoint to disk after each stageThe expensive work survives a crash in the cheap work
Resume from disk on restart, never from zeroRe-running a 25-minute stage to redo a 2-second one is how a day disappears
Claim a lock per runRetries and catch-up fires will otherwise double-publish
Alert on a missed window, don't silently catch upA late success is a failure that lied

Why agents fail differently

A conventional job fails fast and loudly. It gets a connection refused, a non-zero exit, a stack trace, and something pages. The failure has a shape.

An agent waits politely. It issued a reasonable request to a model that is usually slow and occasionally very slow, and it has no way to distinguish "thinking hard" from "never going to answer." Absent an explicit deadline, there is no signal at all — just a process sitting there looking healthy.

That is the real lesson from a thirteen-hour gap. The system was never down. Every component was working. It simply had no opinion about how long anything should take, and in an unattended pipeline that is the same thing as being broken.

What I changed

The guards above are not hypothetical; they are what the pipeline was missing, found by reading its own run log. The lock already existed — a duplicate fire was correctly rejected with "Fire claim was not acquired" — which is the one thing that worked exactly as designed, and the only reason this story does not also include a double-published post.

Everything else is now on the list.
