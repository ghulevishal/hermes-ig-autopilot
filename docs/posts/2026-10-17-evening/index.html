Your quota said 0 of 100, and you were still blocked

Most APIs enforce two limits that count different things. Agents trip the one you cannot see, because verifying your own work costs reads, and reads are free on the meter you are watching.

analysis2026-10-17·3 min read·on Instagram

At 14:38 today an automated pipeline of mine tried to publish a carousel to Instagram and got this back:

`` POST /me/media_publish 403 code 4 / 2207051 "Application request limit reached" ``

Reasonable enough — presumably I had used up the day's posting allowance. So I checked:

`` GET /me/content_publishing_limit quota_total 100 quota_usage 0 ``

Zero of a hundred posts used, and simultaneously blocked for exceeding a limit.

Both of those responses are correct. They are reporting on two different meters.

Quota and rate limit are not the same thing

A quota counts outcomes. Posts published, emails delivered, rows written, messages sent. It is the number a product manager cares about, it maps to your plan tier, and it is almost always the one exposed on a usage endpoint or a dashboard page.

A rate limit counts calls. Every HTTP request against the platform, regardless of what it did or whether it changed anything. Reads count. Failed calls count. Retries count.

Meta documents these as separate systems — Platform Rate Limits sit at the application level, while Business Use Case limits and content-publishing quotas are tracked per asset. One does not decrement the other.

Most APIs with any maturity work this way. You are usually watching the wrong one.

Why this hits agents harder

A conventional application has a roughly predictable read-to-write ratio. An agent does not, because a well-built agent verifies its own work.

It publishes, then reads back to confirm the publish landed. It polls a container until processing finishes. It lists recent items to check for duplicates before acting. It takes a metrics snapshot afterwards. Each of those is a call. None of them is an outcome.

In the pipeline that got blocked today, one published post costs somewhere north of fifteen API calls and exactly one unit of quota. The ratio is roughly fifteen to one against the meter I could not see.

And the painful part: that verification traffic is correct. I have written at length that an agent reporting "done" without reading back from the system of record is making an unverifiable claim. That remains true. It is also precisely what exhausts the rate limit.

Two good practices, in direct tension. Nobody tells you that up front.

Four fixes

Read the usage headers, not the quota endpoint. Most platforms return live consumption on every response — Meta uses X-App-Usage and its business-use-case equivalents. That header is the meter that stops you. The quota endpoint is the one that reassures you while you are being throttled.

Batch verification. One list call that returns twenty items beats twenty individual reads. Verify a batch after a run rather than each item during it. This is the single biggest reduction available and it changes nothing about how rigorous the verification is.

Exponential backoff with a cap. A retry against a tripped limit does not reset the window; on several platforms it extends it. I retried twice today before stopping, which made the wait longer than if I had simply waited.

Treat throttling as expected load, not an error. If a 429 or a 403 only ever reaches a catch block at the top of your run, the agent will treat a routine condition as a crash and discard work in progress. Throttling should be handled where the call is made, with a queue and a delay, not where the stack unwinds.

The uncomfortable bit

The reason this went unnoticed in my own system is that I had been adding verification steps all week — each one individually justified, each one making the agent more honest about what it had actually done.

Nobody adds a read and thinks about the budget, because reads feel free. On the meter you are watching, they are.
