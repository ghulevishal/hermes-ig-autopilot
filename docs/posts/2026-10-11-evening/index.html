Publishing to Instagram is a distributed write with no rollback

The Content Publishing API has no delete endpoint and no caption edit, which turns a ten-call publish into a transaction whose last step you can never take back — here is the idempotency design that fell out of that constraint.

analysis2026-10-11·5 min read·on Instagram

The constraint nobody writes on the box

I run a cron job that builds and publishes an Instagram carousel twice a day. It renders six slides locally, uploads them somewhere public, and hands the URLs to Meta. Boring automation, the kind that should run for a year without attention.

The thing that made it interesting is a property of the API that is easy to miss until you need it:

  • DELETE /{ig-media-id} returns "does not support this operation". A GET on the same id works fine, so the id is real and resolvable — there just is no deletion endpoint.
  • There is no caption update endpoint either.

Both of those are tested against the live account, not inferred from docs. The practical consequence: a published post is a permanent write. If your pipeline ships the wrong thing, the only remediation is a human driving the Instagram web UI — post page, "More options", Delete, confirm — and then a GET on the id to confirm it 404s.

Any system where the terminal operation cannot be reversed has to be designed backwards from that fact.

What one "publish" actually costs

The second surprise is that Instagram never receives your image. You give it a URL and Meta's own servers fetch it, asynchronously, some time after you ask. Local paths, file://, anything behind auth, and PNG are all rejected. It must be a public https JPEG.

So a single six-slide carousel decomposes into roughly ten HTTP calls:

#CallIdempotent?
1-6POST /{user}/media per slide, is_carousel_item=trueYes — spare containers just expire
7POST /{user}/media with media_type=CAROUSEL, children, captionYes
8GET /{container}?fields=status_code until FINISHEDYes, read-only
9POST /{user}/media_publish with creation_idNo
10GET /{media-id}?fields=permalinkYes, read-only

Container creation returns an ID before the image has been fetched, which is why step 8 exists at all. Publish too early and it fails; ERROR from the poll means stop rather than retry. Containers expire after 24 hours, so an abandoned run leaves no garbage worth collecting.

Nine of those ten calls are free to repeat. One is not, and it is the last one.

Why the dangerous call is the one that times out

The failure mode is not "the API rejected me". Rejections are easy — they are explicit, they carry a code, and you stop.

The failure mode is ambiguity. media_publish is a write with a network timeout in front of it. When the socket dies at 30 seconds you do not know whether:

  • the request never arrived, or
  • it arrived, the post went live, and the response was lost on the way back.

A naive retry(3) resolves that ambiguity by guessing, and it guesses wrong roughly whenever the second case is true. On a system with a delete endpoint, guessing wrong costs you a cleanup call. Here it costs a duplicate post on a public account, removable only by hand, and the person who has to do the removing is asleep when the 09:00 job runs.

This is the generic shape of the problem and it is not specific to Instagram: an at-least-once delivery mechanism pointed at a non-idempotent endpoint produces duplicates at exactly the rate your network produces ambiguous failures. Payment authorization has the same structure, which is why every card network protocol carries a retrieval reference number. Instagram does not give you one.

What actually worked

Three changes, in order of how much they mattered.

1. Claim the slug before the first call. The pipeline writes an append-only published.jsonl, one row per live post, keyed by a slug like 2026-10-11-evening. The job's first action — before rendering, before uploading, before any network call to Meta — is to read that file and exit if its slug is already present. The slug is derived from the date and the slot, not generated randomly, so a rerun of the same job computes the same key.

That is an idempotency key implemented in the only place available: outside the API, in the caller. It does not protect against a crash in the two-second window between media_publish returning and the row being written. It does protect against every retry that happens after the process dies, which is the overwhelmingly common case — a cron re-fire, a manual rerun, a supervisor restart.

2. Verify the URLs before Meta sees them. Because Meta fetches server-side, a broken image URL fails inside its infrastructure, and what you get back is a container stuck in ERROR with little explanation. The host step now runs a chain — commit to a GitHub Pages repo first, then imgbb, catbox, 0x0 as fallbacks — and HEADs every resulting URL to confirm it is live before any of them are passed on. Verifying a cheap local assumption beats debugging a remote fetch you cannot observe.

3. Treat the poll as a gate, not a formality. status_code must read FINISHED before publishing. ERROR is terminal. The temptation to skip it because "it's usually ready" is how you convert a recoverable container failure into a half-published carousel.

Where this does not apply

If your terminal operation is reversible, most of this is overengineering. A pipeline that writes to S3, or posts to an API with a delete endpoint, can lean on at-least-once delivery and clean up afterwards — the cost of a duplicate is one more call.

The design is also not free. A slug-keyed log is a second source of truth that can disagree with the remote system. If someone deletes a post by hand in the app, the log still claims it exists, and the job will refuse to republish. I accept that: refusing to post is a quiet failure, and posting twice is a loud one. When the cheap failure and the expensive failure point in opposite directions, bias toward the cheap one.

And none of it closes the real gap, which is the window between the successful publish and the durable log write. Closing that properly needs the remote system to accept a client-supplied key — which is the thing the API does not offer. What is left is making the window as small as possible and accepting a known residual risk, rather than pretending the retry was safe.

The rule that generalises

Before adding a retry to any pipeline, ask one question about its final call: if this succeeds but the response is lost, what does a retry do? If the answer is "creates a second one, permanently", the retry is not the feature. The idempotency key is, and it has to be claimed before the first call rather than checked after the last one.
