Guardrails are not prompts, and humans are not a guardrail

If a better prompt could get past it, it was never a control. A practical split between the things an agent cannot do, the things a human must approve, and how to decide which is which without drowning in approvals.

analysis2026-10-17·3 min read·on Instagram

The first thing most engineers do when they give an agent real access is write a rule into the system prompt. Don't touch production. Don't delete anything. Ask before spending money.

Then they treat that sentence as a safety boundary.

It isn't one. It's a request, and the test is simple: if a better prompt could get past it, it was never a control. Anything you ask the model to do, the model can fail to do — through a bad plan, an ambiguous tool result, or a chain of individually reasonable steps that arrives somewhere unreasonable.

Two different tools

A guardrail means the agent cannot. It is enforced outside the model, by something the model cannot talk to:

  • A credential scoped so production is not reachable
  • A dry-run default where publishing needs an explicit --live flag
  • A spend cap that trips at a number
  • An allowlist of permitted actions

The agent can plan whatever it likes. The boundary does not care.

Human-in-the-loop means the agent waits. A person looks and decides. It is far more flexible than a guardrail — a human can catch a bad idea that is technically permitted — and far more expensive, because it spends attention, and attention does not scale.

These are not interchangeable, and the common failure is reaching for the second when the first would do.

Approval fatigue is a real failure mode

Put a human on everything and you get a reviewer who approves forty things a day. By the fortieth they are clicking, not reading. The forty-first — the one that matters — gets the same click.

That is worse than having no review at all, because now there is a rubber stamp with a person's name on it, and everyone downstream believes the thing was checked.

Anyone who has run a change-approval process has watched this happen. The number of gates is not the same as the amount of safety, and past a certain density, adding gates reduces it.

Gate on blast radius

The useful question is not "is this task complex?" or "is this risky-sounding?" It is what happens if this is wrong, and can I take it back?

ActionControl
Reversible, cheapLet it run. Log it.
Reversible, costlyLet it run. Alert after.
IrreversibleNamed human approves, every time.

Irreversible is a shorter list than people expect, and a more obvious one: deletes, payments, anything that sends to another human, anything that becomes public. Those get a person. Everything else gets a guardrail and a log.

A worked example from this pipeline: publishing to Instagram is irreversible — the API has no delete endpoint, so a bad post cannot be withdrawn programmatically. It requires explicit approval and an explicit --live flag, and the default is a dry run that prints what would happen. Rendering slides is reversible and free, so it runs unattended with no gate at all. Same system, two different controls, chosen by consequence rather than by how clever the step is.

Five controls that actually hold

None of these live inside the prompt.

  • Scoped credentials. The agent cannot reach what it must not touch. This is the highest-leverage control and the one most often skipped, because handing over your own full-access key is easier.
  • Dry-run by default. The destructive path requires an explicit flag. Make the safe thing the default and the dangerous thing deliberate.
  • Spend and rate caps as circuit breakers. Not warnings — breakers. A warning is a log line nobody reads at 2am.
  • Allowlist the actions, don't blocklist the bad ones. You cannot enumerate every bad action. You can enumerate the good ones.
  • One named human per irreversible action. Named, not "the team". Shared ownership of an approval is nobody's ownership.

The part that transfers from infrastructure

None of this is new. It is least privilege, staged rollout, blast-radius thinking and change control — the same practices that keep distributed systems alive, pointed at a non-deterministic component.

What is new is that the component argues back. A microservice does not attempt to reason its way around an IAM policy. An agent will cheerfully construct a plan that routes around your intent while satisfying every instruction you wrote.

Which is exactly why the control cannot be an instruction.
