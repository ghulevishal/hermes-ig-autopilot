Every server is 99% fast and your system is slow 63% of the time

Fan-out turns rare per-server slowness into common whole-system slowness. Here is the arithmetic, and the one cheap technique that masks it.

analysis2026-11-03·4 min read·on Instagram

The arithmetic nobody runs before shipping

Take a service where each server responds in about 10ms, but with a 99th-percentile latency of one second. One request in a hundred is slow. On a single server that is easy to shrug off.

Now make one user request wait on 100 of those servers in parallel and return only when all have answered. The chance that every server lands in its fast 99% is 0.99^100 = 0.366. So 63% of user requests take more than a second — even though every individual server is fast 99% of the time.

The formula is worth memorising, because it is the whole point:

`` P(request is slow) = 1 - (1 - p)^n p = per-server probability of a slow response n = number of servers the request fans out to ``

1 in 10,0002,00018%

Rare slowness becomes common slowness. Your p99 is not set by your code; it is set by the worst machine any single request happens to touch.

Why this is now an agent problem

In 2013 the fan-out was web search touching thousands of leaf servers. In 2026 it is every agent and RAG system you build. One user turn becomes a planner call, a batch of tool calls, several retrieval lookups and a synthesis call — often in parallel, often waiting for all of them. That is scatter-gather with a different vocabulary, and the arithmetic does not care what you call it.

Two consequences fall straight out of the table:

  • Count your dependencies before you promise a latency target. Ten parallel calls, each slow 1% of the time, make roughly one request in ten slow. Adding a dependency raises the tail even if its average looks harmless.
  • Measure percentiles per step, not averages per request. An average hides the one call that stalled. Report p50, p95 and p99 for each hop and for the whole request.

The fix: tolerate the tail, do not chase it

Dean and Barroso's key move is an analogy to fault tolerance. You do not eliminate unreliable components; you mask them. You do not eliminate latency variability either — shared CPUs, background daemons, queueing and GC guarantee it — so you build a predictable whole out of unpredictable parts.

The most useful technique is the hedged request:

1. Send the request to the replica you believe is best. 2. If it has not answered by its 95th-percentile expected latency, send a second copy to another replica. 3. Take whichever answers first and cancel the other.

Triggering at p95 is what makes it cheap: by definition only ~5% of requests ever fire a second copy, so you pay a few percent more load to cut the tail hard. In Google's own BigTable benchmark — reading 1,000 keys spread across 100 servers — hedging after a 10ms delay dropped the 99.9th-percentile latency from 1,800ms to 74ms while sending just 2% more requests.

The reason it works is that the slowness usually is not inherent to the request. It is interference: the first replica was unlucky and sat behind a queue or a background job. A fresh replica simply does not have that problem right now.

If you need to be more aggressive, tied requests enqueue the job on two servers at once and let each cancel the other's copy the instant one starts executing — removing the hedge delay. In the paper that cut 99.9th-percentile reads by about 38% for under 1% extra disk load.

Where it bites

Hedging is not free and it is not universal. The failure modes are specific:

  • Never hedge a write or a non-idempotent action. A duplicated read is waste; a duplicated payment, email or state mutation is an incident. If the operation has side effects, you need an idempotency key before you hedge, so the second copy collapses into the first.
  • It masks variance, not saturation. If the backend is genuinely overloaded, a second copy adds load to the thing that is already drowning. Hedging assumes spare capacity on the other replica.
  • Cap the hedge rate. p95 triggering keeps you near 5%, but a mis-set threshold or a correlated slowdown can send the hedge rate toward 100% and double your traffic exactly when you can least afford it. Put a hard ceiling on the fraction of hedged requests.
  • For model generations, cost replaces disk. Hedging a retrieval costs a cache lookup. Hedging an LLM generation costs a second full generation — real money — so reserve it for the cheap, idempotent hops (retrieval, classification, tool reads) rather than the expensive tail.

The decision rule

Put it on a card:

  • Trigger on p95 latency, not a fixed timeout — it self-tunes as the system changes.
  • Hedge reads and lookups; never writes, payments or any side-effecting action without an idempotency key.
  • Cap hedges near 5% of traffic.
  • Remember it buys you nothing against a saturated backend — that is a capacity problem, not a tail problem.

The headline is uncomfortable and correct: in a fan-out system, the question is never "is my average fast." It is "how many things does one request touch, and how slow is the unluckiest of them." Answer that before you promise anyone a latency SLO.
