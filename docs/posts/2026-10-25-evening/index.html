Prompt caching: the TTL starts when you send

A 4-minute stream leaves about one minute on Anthropic's 5-minute cache. Structure the prefix so hits are the default, pick TTL from traffic shape, and treat a zero in the usage fields as a miss — not as "caching is on".

analysis2026-10-25·6 min read·on Instagram

Most agent stacks pay full input price for tokens the model has already processed. The tools array, the system prompt, the policy document, the few-shot examples — they are identical on turn 12 and turn 1. Prompt caching is the vendor feature that stops you being billed as if they were new. The part that actually fails in production is not "did we turn it on". It is that the clock starts when the request leaves, the prefix has to match byte-for-byte, and a miss is silent.

This is a technique post, not a model roundup. The numbers below are vendor-published as of 25 October 2026. They will move. The layout of the prompt will not.

What a cache hit actually is

When a model reads a prompt it builds key-value states for the tokens it has seen so far. Prompt caching stores those states for a prefix — the unchanged tokens at the front of the request — and reuses them on a later request that starts the same way. The model still processes the new tail and still generates a new answer. Identical requests are not guaranteed to produce identical outputs. OpenAI states this in its FAQ; treat it as a cost and latency optimisation, not as a reproducibility feature.

Anthropic caches the full prefix in a fixed order: tools, then system, then messages, up to and including the block marked with cache_control. You can use automatic caching (one top-level cache_control) or up to four explicit breakpoints. OpenAI caches the rendered context — developer messages, tool definitions, conversation history — and, on GPT-5.6 and later, lets you place explicit breakpoints as well. Implicit caching remains the default.

The match is exact. Change the tool description, reorder the tools array, swap the model, or edit one character in the system prompt, and everything after that change misses. Anthropic's platform article is blunt: cache reads must be byte-exact across the full span, on the same model.

The number that is not the headline

On Claude Opus 5.5, base input is $4 per million tokens. A 5-minute cache write is $5. A cache hit is $0.20 — 0.05x, not the 0.1x that still applies to most other Claude models. Sonnet 5.5 is the same multiplier on a $2 base: write $2.50, hit $0.10. Anthropic's docs footnote this. Collapsing "Claude cache hits are 90% off" into one number is how you mis-price Opus 5.5 by a factor of two.

The 5-minute write is 1.25x base input. The 1-hour write is 2x. Cache breakpoints themselves are free. Break-even on the 5-minute TTL is the second request that reuses the prefix. If the prefix is used even once inside the TTL, you are ahead of sending it uncached twice.

OpenAI's current guide says cached input is discounted by up to 95%. On GPT-5.6 and later, cache writes cost 1.25x the uncached input rate; subsequent reads cost 0.1x on most of those models and 0.05x on GPT-6.1 Sol. The default lifetime is 30 minutes after the most recent write or reuse (prompt_cache_options.ttl only accepts 30m). OpenAI also states that cached tokens still count toward tokens-per-minute rate limits. Do not assume a cache hit is free quota.

I did not independently measure any of these multipliers. They are what the vendor pages said on 25 October 2026.

The trap: the clock starts at send

Anthropic's prompt-caching docs:

The lifetime is measured from the start of the request that writes or reads the cache entry, not from the end of its response. Time spent generating a response counts against the lifetime: if a response takes 4 minutes to stream, a follow-up request that reuses the same cached prefix must start within about 1 minute of that response completing.

That is the hook. A long generation does not wait for the TTL to start. It consumes it.

The same page, and Anthropic's "Reducing cost and improving performance" article, describe the agent-shaped version of this. If a parent request blocks on a tool call or a sub-agent for longer than the TTL, the prefix expires before the result comes back. The next turn rewrites the cache at 1.25x (or 2x for the 1-hour TTL) instead of reading it cheaply. The fix is not "retry harder". It is to set {"type": "ephemeral", "ttl": "1h"} on the stable prefix when the work between turns can exceed five minutes, or to keep the parent cache warm with a request that actually reuses it.

A 5-minute TTL that is hit refreshes for no extra charge. Use it when traffic is denser than five minutes. Use the 1-hour TTL when it is not. Mixing both in one request is allowed, with the constraint that longer-TTL blocks must appear before shorter-TTL ones.

Minimum length fails closed, and silently

Shorter than the model's minimum cacheable length means the prefix is not cached. Anthropic does not error. Both cache_creation_input_tokens and cache_read_input_tokens stay 0. On the Claude API the current minimums include 512 tokens for Opus 5.5, Sonnet 5.5 and Haiku 5.5, 1,024 for several 4.x/5.0 lines, and 4,096 for Opus 4.6/4.5 and Haiku 4.5. OpenAI's minimum is 1,024 tokens for GPT-5.6 and later; hidden system tokens do not count toward it.

If you are "using caching" and both fields are zero, you are not using caching. You are sending a prompt that did not qualify.

OpenAI shipped Prompt Cache Diagnostics for GPT-5.6 and later in the Responses API (docs dated 24 October 2026). You pass prompt_cache_options.comparison_response_id against a baseline response and read prompt_cache_diagnostics for a miss reason. Use it when hit rate drops and you cannot see why. Anthropic exposes cache_creation_input_tokens, cache_read_input_tokens and input_tokens (tokens after the last breakpoint) on every response. Total input is the sum of the three. Console diagnostics exist for the same reason.

What to do on Monday

1. Put the stable material first, in the order the provider hashes: tools, then system, then reference docs. Put the new user turn last. Do not timestamp the prefix. Do not inject a request id into the system prompt. 2. Keep the prefix byte-exact and on one model. A "router" that silently swaps Sonnet for Haiku between turns is a cache miss generator. 3. Pick TTL from the gap between turns, not from a default. Dense chat: 5-minute, it refreshes free. Agent with tools that can run past five minutes: 1-hour on the stable prefix. 4. Read the usage fields on every response and alert when cache_read_* (or cached_tokens) is zero on a request you expected to hit. A miss is an incident, not a curiosity. 5. Do not pad junk to hit the minimum. If you expand a prefix to qualify, expand it with instructions or examples that change behaviour in a way you have evaluated. 6. Remember what caching does not do. It does not make outputs identical. It does not skip output tokens. On OpenAI it does not reduce TPM consumption.

Where this does not apply: one-shot prompts with no shared prefix, traffic so sparse that even a 1-hour TTL never hits, and prefixes under the minimum that you cannot honestly enlarge. In those cases you are buying a write premium for no read. Leave it off and spend the attention on routing, which is a different lever.

The saveable version is the same list without the prose. Stable first. Variable last. Same model. TTL from the gap. Measure the hit. If the field is zero, you paid full price.
