Your retries are the outage

Retries don't add across a call path - they multiply, and they switch on at the exact moment a dependency is already failing. Here is the budget that stops a retry storm.

analysis2026-11-17·5 min read·on Instagram

The failure mode nobody configured on purpose

Almost every service you run retries failed calls. Most of the time you never chose that behaviour: it lives inside an HTTP client, a service mesh, an SDK default, or a framework you adopted for other reasons. A 2026 systematic study of 200 open-source Python microservice projects found explicit retry logic in only 11.5% of them, and the authors' own audit put the true figure nearer 41% once framework defaults were counted. The retries are there. They are just not written down anywhere a reviewer would see.

That invisibility is the problem, because retries are not a local setting. Their danger is a system-level property that only appears when several layers interact under failure.

Retries multiply, they don't add

Number the layers in a request path from the user down to the dependency that fails. If each layer retries up to three times, a single failed call at the bottom can generate (1 + retries) attempts at every level, and those multiply:

PathMax attempts at the bottom
2 tiers, 3 retries each4 x 4 = 16
3 tiers, 3 retries each4 x 4 x 4 = 64
4 tiers, 3 retries eachup to 81

A gateway with 2 retries, a service with 3, and a database client with 3 produces 3 x 4 x 4 = 48. At 1,000 requests per second, a hard-down dependency receives up to 48,000 attempts per second - while users still get errors. The mechanism has a name in the recent literature: the retry amplification factor.

The cruel part is the timing. Under normal conditions the retry logic is invisible - almost nothing fails, so almost nothing retries, and the expected amplification under independent, random failures is only about 2x. The multiplier only switches fully on when the dependency is already saturated, because then every attempt fails and every layer's retries fire on every request. The mechanism that was supposed to add resilience becomes the load that guarantees the outage.

The counter-intuitive measurement

It is tempting to assume that retries can only help: worst case, they are wasted work. The data says otherwise. In the same 2026 study's simulation (n = 100 trials per strategy), under correlated failure a naive standard retry policy reduced request success from 55.4% (performing no retries at all) to 41.5%. Adding retries made the system fail more often, precisely when resilience was needed.

Three effects drive the inversion. Queue slots are the scarce resource, and a retry competes with fresh traffic rather than deferring to it, so both are rejected more often. Each attempt consumes processing time before it fails, so latency climbs until callers abandon requests that might otherwise have completed. And at high failure rates, most retries could never have succeeded anyway, so the capacity they burned produced nothing.

Note the scope honestly: this is a simulation under correlated failure, not a production measurement, and the paper is a preprint. The worst-case 81x is also a bound, not a forecast - finite queues shed load and truncate it long before it gets there. But the direction of the effect is the point, and it matches what outage post-mortems have shown for years.

Where agent systems make it worse

If you build on LLM providers, you already live inside a deep, fan-out call path - and you probably have more retry layers than you think. The model SDK retries on a 429. The gateway or proxy in front of it retries. Your agent framework retries a failed tool call. Your own orchestration loop retries the step. When the provider rate-limits you, all of those fire on the same signal at once, and the aggregate request rate you send into an already-throttled endpoint goes up, not down. The cooldown you were trying to escape gets longer because you kept knocking.

This is the same shape as a classic retry storm, with the model provider as the saturated dependency. The fix is the same too.

The retry budget: design it as a system

None of the countermeasures require a rewrite. They require deciding retry behaviour once, across the whole path, instead of per call site.

  • Retry budget. Cap retries as a fraction of total requests - a common target is no more than 10% of traffic may be retries. The Google SRE book gives a concrete illustrative example: allow only ~60 retries per minute in a process, and once the budget is spent, fail fast instead of retrying. The effect is that retries collapse toward zero exactly when failure is widespread, which is exactly when you want them to.
  • Retry at one layer only. Pick the layer nearest the failing dependency and let it own retries; every layer above fails fast. This converts the multiplicative product back into a single 1 + r. Check your HTTP client, SDK, mesh and gateway first - one of them is probably already retrying.
  • Cap attempts per request. Three total attempts is a sane default. Never retry a given request indefinitely.
  • Exponential backoff with jitter. Backoff spreads the spike over time; jitter breaks the synchronized wave that forms when independent clients back off in lockstep. In that 2026 survey, exactly one of 113 production configurations randomized its delay - almost nobody adds jitter, and without it a network blip becomes a periodic surge. Backoff changes when retries happen, not how many; it is not a substitute for a budget.
  • Deadline propagation. Pass one shared deadline down the whole call path so upstream tiers stop retrying the moment the overall budget is spent, instead of each tier retrying against its own private clock. The clock does not restart when you retry.
  • Honor overload signals. A 429 or 503 with Retry-After is the dependency telling you to stop. Respect it, propagate "overloaded, do not retry" up the stack, and reach for a circuit breaker - which turns a slow failure into a fast one and gives the dependency room to recover - rather than retrying into the wall.

Where this does not apply

Retries are not the enemy; unbudgeted, layered, correlated retries are. For transient, independent faults - a dropped packet, a brief leader election - a single bounded retry with jitter is the right tool and genuinely raises success. The guidance also assumes idempotency: retry reads, lookups and idempotent writes freely, but a retried non-idempotent write or payment is a duplicate side effect, which is a different and worse failure than an error.

The one action that pays for itself: map the retry counts across a full critical path, multiply them, and ask whether the slowest service in the chain can survive that multiple of its normal request rate. If the answer is no - and it usually is - you are not looking at a safety net. You are looking at a latent retry storm waiting for its trigger.
