The environment variable that breaks every Python on the machine

An absolute path to the interpreter pins which binary runs, not where that binary looks for code — and on a box running an agent runtime, PYTHONPATH is an unversioned global that every child process silently inherits.

analysis2026-10-12·5 min read·on Instagram

The symptom

A cron job that renders Instagram carousels died on import:

`` ImportError: cannot import name '_imaging' from 'PIL' ``

The same script, run by hand in a terminal two minutes later, worked. Same machine, same user, same file. The usual suspects were all clean: Pillow was installed, the install was recent, nothing had been upgraded that day.

The standard move at that point is to stop trusting python3 on PATH and pin the interpreter explicitly. I did. /usr/local/bin/python3, which resolves through a symlink to Python.framework/Versions/3.12/bin/python3 — CPython 3.12.5. Still broke.

That is the interesting part. Pinning the binary is supposed to be the end of the ambiguity, and it did not move the failure at all.

What was actually happening

A probe script, run twice from the same shell, with the only difference being the environment:

```

A: inherited env, absolute system interpreter

exe : /usr/local/bin/python3 PYTHONPATH : /Users/.../venv/lib/python3.14/site-packages PIL : FAIL ImportError cannot import name '_imaging' resolved from: /Users/.../venv/lib/python3.14/site-packages/PIL/__init__.py

B: same interpreter, PYTHONPATH stripped

exe : /usr/local/bin/python3 PYTHONPATH : <unset> PIL : OK 11.1.0 /Library/Frameworks/Python.framework/Versions/3.12/lib/python3.12/site-packages/PIL/__init__.py ```

The agent runtime that launches the cron job exports PYTHONPATH at its own virtualenv, which is built on CPython 3.14. Every process it spawns inherits that variable, and so does every process those spawn.

Printing sys.path under the inherited environment shows the whole mechanism in one screen:

indexentry
0the script's own directory
1.../venv/lib/python3.14/site-packages ← PYTHONPATH
2–4the 3.12 standard library and lib-dynload
5.../python3.12/site-packages ← the real one

PYTHONPATH is not appended. It is prepended, ahead of the standard library itself. So a 3.12 interpreter went shopping in a 3.14 virtualenv and found a perfectly real PIL/ directory there — Pillow 12.3.0, as it happens, versus the healthy 11.1.0 one level further down the path.

Why the error named the wrong thing

Pillow is a hybrid package. PIL/__init__.py is pure Python and imports into any interpreter without complaint. The actual image work lives in C extensions, and those carry an ABI tag in the filename:

`` _imaging.cpython-314-darwin.so _imagingft.cpython-314-darwin.so _imagingcms.cpython-314-darwin.so ``

cpython-314 means CPython 3.14 on this platform. A 3.12 interpreter will not load it — it will not even consider it a candidate, because the tag does not match. So the import of PIL succeeded, the import of PIL._imaging found nothing, and the traceback blamed a package that was not the one I installed, at a path I never typed.

That is the part worth keeping. The error message pointed at Pillow. Pillow had nothing to do with it. The failure was an environment variable set by a different process, three layers up, for a different interpreter.

The general shape of the bug

Strip out the Python specifics and the pattern is familiar to anyone who runs services:

  • The environment block is a process-global, unversioned, implicit argument. It is inherited by default, it is not declared anywhere in the code, and nothing validates it.
  • It crosses the boundary you think you are controlling. Pinning the binary controls which program runs. It says nothing about the search path that program uses to resolve its own dependencies. Same class of problem as LD_LIBRARY_PATH for native binaries, NODE_PATH for Node, or a JAVA_TOOL_OPTIONS someone exported for an unrelated agent.
  • It reproduces only in the child. My interactive shell had a different environment from the cron job's, which is exactly why "works on my machine" was literally true and completely useless.
  • A virtualenv is not a sandbox. It is sys.path manipulation plus a convention, and PYTHONPATH beats the convention. Activating one does not protect you from a variable the parent exported.

The SRE reading of it: this is configuration arriving through an undeclared channel. Everything we do to make config auditable — version it, validate it at startup, fail loud on an unknown value — we skip entirely for the environment block, which is the one input every process accepts silently.

The fix

Not in the code. The code never sees the decision; by the time import PIL runs, sys.path has already been built. So the fix has to be at the process boundary, which means a launcher:

``bash exec env -u PYTHONPATH -u VIRTUAL_ENV "$PY" "$IG_DIR/scripts/$script" "$@" ``

Three things are doing work in that line:

1. env -u removes the inherited variables rather than overwriting them. Setting PYTHONPATH="" is not the same thing — an empty string can still be interpreted as a path entry. 2. $PY pins the interpreter, which is still necessary, just not sufficient. 3. exec replaces the shell rather than forking under it, so the process tree stays flat and signals reach the real process.

Then the operational half: no script is ever invoked directly. Everything goes through ./ig <command>, and the preflight check asserts that the import actually works before cron is allowed to trust the pipeline. A rule that is only written in a comment gets violated the first time someone is in a hurry, including by me.

Where this does not apply

  • If you control the full process tree — a container with an explicit ENV block, a systemd unit with Environment= — then scrubbing at every leaf is noise. Set it once at the top and assert it.
  • If your dependencies are pure Python, the mismatch may never surface. The ABI tag is what turns a quiet shadow into a hard failure, which is a mercy: a silently wrong version of a pure-Python library is the worse outcome.
  • Scrubbing VIRTUAL_ENV is wrong if the thing you are launching is genuinely supposed to run inside that venv. The launcher pattern works because these scripts have no relationship to the agent runtime's environment at all.

The rule I took away

When a process fails only under a scheduler, compare environments before you compare code. And when a pinned absolute path does not change a failure, that is a signal rather than a dead end: the problem is not which program is running, it is what that program is allowed to see.
